## 1. 목표 end-state

Durumi를 "마크다운 파일 하나를 여는 에디터"에서 **원고 워크스페이스**로 확장한다. Visual Studio의 Solution/Project에 대응하는 단위로, 하나의 프로젝트가 다음을 함께 담는다:

- 원자료(raw data)
- Python 분석 스크립트
- 그림(figures)과 표(tables)
- 원고(manuscript)
- 참고문헌(references)
- 저자(authors)·감사의 글(acknowledgements)
- ClinicalTrials.gov 등록번호

여기에 CLI 에이전트(Claude Code, Codex, grok build, oh-my-pi)가 **디스크의 파일을 직접 생성·수정**하고, 사용자는 Copilot과 유사한 **제안–승인(propose-and-approve)** 흐름으로 그 변경을 수용하거나 거부한다.

이 end-state는 두 가지를 동시에 요구한다:
1. 에디터가 **자기가 쓰지 않은 파일 변경을 안전하게 흡수**할 수 있어야 한다.
2. 에디터가 **연 적 없는 종류의 파일(`.py`, `.bib`, `.csv`, `.json`)도 바이트 손상 없이 다룰 수 있어야 한다.**

## 2. 확정된 아키텍처 결정

### 2.1 CodeMirror 6 유지 — 문서모델 에디터로의 교체는 기각

ProseMirror / Lexical / Slate를 검토했고 **기각**했다. 결정 근거는 "지금 잘 동작하니까"가 아니라, §1의 end-state가 편집 엔진에 부과하는 네 가지 요구다:

| 요구 | CodeMirror 6 (텍스트 버퍼) | 문서모델 에디터 (트리 → 직렬화) |
|---|---|---|
| (a) 바이트 정확 보존 | 버퍼가 곧 파일 바이트 | 트리를 마크다운으로 재직렬화 — 스키마 밖 문법은 소실 |
| (b) 외부 변경 흡수 | 텍스트 diff를 그대로 dispatch | 외부 텍스트를 파싱→트리 재구성→커서 재매핑 필요 |
| (c) 통합 diff 적용·표시 | 라인/오프셋 단위가 diff 단위와 일치 | diff 단위(라인)와 편집 단위(노드)가 어긋남 |
| (d) 비마크다운 파일 편집 | `@codemirror/language-data`로 즉시 지원 | 마크다운 전용 스키마 — 지원 없음 |

특히 (a)는 에이전트가 **사용자와 같은 파일을 쓴다**는 전제에서 타협 불가다. 문서모델 에디터는 자신이 이해하지 못하는 문법을 조용히 지운다.

부수 근거(결정의 이유가 아니라 비용 확인): `@codemirror/*` / `@lezer/*`를 import하는 파일은 95개, 14,328 LOC이며 이는 `src`+`electron`+`shared` 전체 41,585 LOC의 약 34%다. `src/editor/` 자체 확장만 1,908 LOC, 에디터 관련 테스트는 76개 파일이다. 교체 비용은 크지만, **비용이 아니라 위 4개 요구가 결정을 만든다.**

### 2.2 단일 파일 열기는 보존된다

`.md` 파일 하나를 여는 오늘의 동작은 **그대로 유지**된다. 프로젝트에 속하는 것은 **선택**이며, "프로젝트 없음(no-project)"은 예외 상태가 아니라 **1급 상태**다. Epic의 모든 기능은 이 상태에서 합리적으로 동작해야 한다.

### 2.3 실시간 협업은 Epic 전체에서 제외

CRDT/OT, 원격 커서, 세션 서버는 v0.3·v0.4 어디에도 없다. `product.md` §5의 out-of-scope 선언을 유지한다.

## 3. 워크스페이스 모델

```
프로젝트 루트 (매니페스트 파일이 있는 디렉터리)
├── <매니페스트>            프로젝트 정체성 + 폴더 재정의 + 프로젝트 수준 메타데이터
├── data/                   원자료 (읽기 위주, 에이전트가 생성)
├── scripts/                Python 분석 스크립트 (v0.4 샌드박스 대상)
├── figures/                생성된 그림 (스크립트 산출물)
├── manuscript/             원고 마크다운 (+ front matter = 원고 수준 메타데이터)
└── reference/              참고문헌 파일 — 기존 v0.1.7 관례 그대로
    references.bib          기존 walk-up 탐색 대상 그대로
```

계층은 4단이다: **프로젝트 → 규약 폴더 → 파일 → 문서 메타데이터**. 각 SPEC은 이 계층의 서로 다른 단면을 담당한다.

메타데이터는 세 계층으로 나뉘며, **정본은 원고 front matter다** (SPEC-1 REQ-WS-034가 확정):

| 계층 | 위치 | 역할 |
|---|---|---|
| 1. 원고 front matter | 각 원고의 YAML front matter (`author`, `registration`, `acknowledgements`) | **정본.** 저자·감사의 글·등록번호의 유효값이 여기서 결정된다 |
| 2. 매니페스트 | `durumi.project.yaml` (`authors`, `acknowledgements`, `registration`) | **프로젝트 기본값.** 원고가 해당 키를 선언하지 않았을 때만 쓰인다 |
| 3. `.bib` 파일 | `references.bib` (기존 구현 유지) | **서지 정본.** 위 두 계층은 서지 항목을 담지 않는다 |

**왜 front matter가 정본인가 (SPEC-2~5 설계 시 반드시 전제할 것)**: 한 연구가 본문·보충자료·리뷰어 응답서 등 **여러 원고**를 갖고 그 저자 목록이 서로 다른 것이 의학연구 실무에서 흔하다. 메타데이터를 프로젝트 수준에 두면 이 원고별 차이를 표현할 수 없다. 또한 `shared/manuscriptTemplates.ts`가 이미 `author:`(`:22`)와 `registration:`(`:70` ClinicalTrials.gov, `:168` PROSPERO) front matter 키를 출하하고 있다.

따라서 멀티패널 셸(SPEC-2)의 메타데이터 표면은 **활성 원고 패널에 종속**되어야 하며, 프로젝트 전역 단일 메타데이터 뷰로 설계해서는 안 된다.

| 2 | 멀티패널 셸 | **v0.3** | 1 | 원고 + 스크립트 + 그림을 동시에 보는 패널 레이아웃 |
| 3 | CLI 에이전트 어댑터 | v0.4 | 1, 2 | 외부 CLI 에이전트 실행·수명주기·출력 스트림 |

### SPEC-1 — 워크스페이스 골격 (v0.3, 본 Epic에서 유일하게 전체 작성됨)

프로젝트를 선언하는 매니페스트 파일과 폴더 규약, 열린 문서의 외부 변경 감지·조정, 그리고 저자/참고문헌/감사의 글/등록번호 메타데이터 모델을 정의한다. Epic의 **정확성 핵심**은 여기 있다: 외부 변경 조정이 틀리면 이후 모든 SPEC이 사용자 데이터를 잃는다. 특히 **IME 조합 중 문서 리로드**는 v0.2.19–.28에서 반복된 IME 파손 사고와 같은 위험 계열의 새 사례이므로 일급 요구사항으로 다룬다. 상세: `.moai/specs/SPEC-V03-WORKSPACE-001/`.

### SPEC-2 — 멀티패널 셸 (v0.3)

오늘의 단일 에디터 표면을 다중 패널로 확장한다. 하나의 창에서 원고(마크다운, 3-모드 유지)와 보조 파일(`.py`, `.csv`, `.bib`)을 나란히 열고, 각 패널이 SPEC-1의 감시·조정 계약을 독립적으로 소비한다. 기존 좌/우 사이드바(`sidebarStore` / `rightSidebarStore`)와 충돌하지 않는 레이아웃 모델, 패널별 편집 모드 상태, 패널 포커스와 메뉴 커맨드 라우팅(`useMenuCommandRouter`)의 관계를 정의한다. 비마크다운 파일의 실제 편집 표면(언어별 문법 하이라이팅, 저장 경로)이 여기서 확정된다. 프로젝트 없음 상태에서는 단일 패널로 축퇴한다.

### SPEC-3 — CLI 에이전트 어댑터 (v0.4)

Claude Code / Codex / grok build / oh-my-pi 등 외부 CLI 에이전트를 프로젝트 루트를 작업 디렉터리로 삼아 실행하고, stdout/stderr 스트림을 렌더러로 중계하며, 취소·타임아웃·비정상 종료를 처리한다. 프로세스 spawn은 main 프로세스 전용이며(렌더러는 Node API 없음), 에이전트별 차이는 어댑터 인터페이스 뒤로 감춘다. 에이전트가 파일을 쓰는 순간부터 SPEC-1의 조정 경로가 실전에 놓인다 — 그래서 SPEC-1이 선행이다. 에이전트 실행 권한과 `pathGuard` 신뢰 경계의 관계가 여기서 확장된다.

### SPEC-4 — Diff 승인 UI (v0.4)

에이전트가 만든 파일 변경을 **자동 적용하지 않고** 통합 diff로 제시하고, 사용자가 파일 단위/헝크 단위로 수용·거부한다(Copilot 유사 흐름). SPEC-1이 정의한 "외부 변경 확정" 이벤트를 소비하되, 조정 정책을 "자동 리로드"에서 "승인 대기"로 바꾸는 상위 계층이다. 승인된 변경만 버퍼에 적용되고, 거부된 변경은 디스크로 되돌려진다. 이 SPEC은 SPEC-1의 조정 계약이 정책 교체 가능하도록 설계되어야 함을 역으로 요구한다.

### SPEC-5 — Python 분석 샌드박스 (v0.4)

`scripts/`의 Python 스크립트를 격리 실행하고, 산출 그림을 `figures/`에 쓰며, 원고의 마크다운 블록이 그 산출물을 참조하도록 연결한다. 데이터가 바뀌면 재실행하고 그림을 갱신한다. 실행 격리(인터프리터 탐지, 환경 변수, 네트워크 접근 정책), 실패 처리, 산출물 경로 규약이 범위다. `README.md` 로드맵 항목 4의 구현체다.

## 5. 의존 순서의 근거

- **1 → 3**: 에이전트가 파일을 쓰기 시작하는 순간, "에디터가 열고 있는 파일이 밖에서 바뀐다"가 상시 상황이 된다. 조정 계약 없이 3을 먼저 하면 미저장 편집 소실이 기본 동작이 된다.
- **1 → 2**: 패널은 각자 문서를 열고 각자 감시를 구독한다. 감시·조정 계약이 먼저 있어야 패널 N개에 대해 일관되게 적용된다.
- **3 → 4**: 승인 UI는 승인할 제안 스트림이 있어야 의미가 있다.
- **1 → 4**: 승인 UI는 SPEC-1의 "외부 변경 확정" 이벤트를 소비하고 그 조정 정책을 대체한다.
- **3, 4 → 5**: 스크립트 실행은 에이전트 실행 인프라(프로세스 수명주기)를 재사용하고, 그 산출물은 승인 흐름을 탄다.

v0.3/v0.4 분할선은 **"디스크가 밖에서 바뀔 수 있다"까지가 v0.3, "밖에서 바꾸는 주체를 앱이 직접 띄운다"부터가 v0.4**다. v0.3만으로도 사용자가 별도 터미널에서 CLI 에이전트를 돌리는 워크플로가 안전하게 성립한다 — 이것이 v0.3 단독 출하의 가치다.

## 6. 프로세스·모듈 경계

기존 3-프로세스 + `shared/` 커널 구조(`structure.md` §2)를 **변경하지 않는다.** Epic이 도입하는 책임을 기존 경계에 배치한다:

| 새 책임 | 배치 | 이유 |
|---|---|---|
| 매니페스트 스키마·파싱·검증 | `shared/` | main(탐색·읽기)과 renderer(표시·편집) 양쪽이 같은 타입을 봐야 함 |
| 프로젝트 discovery (walk-up) | `electron/` | 파일시스템 접근은 main 전용 |
| 파일 감시 + 변경 확정(mtime/size 재검사) | `electron/` (`fs.ts` 확장) | 기존 `watchRoot`/`fs:change` 인프라의 확장 |
| 조정(reconcile) 정책·충돌 UI·IME 게이트 | `src/` | 조합 상태와 CodeMirror 뷰는 렌더러에만 있음 |
| 신규 IPC 채널 | `shared/ipc-contract.ts` | IPC 계약 SSOT — 채널 추가는 반드시 여기 |
| 패널 레이아웃 상태 (SPEC-2) | `src/store/` | 기존 zustand 스토어 계열 |
| 에이전트 프로세스 spawn (SPEC-3) | `electron/` | `child_process`는 main 전용 |
| Python 샌드박스 실행 (SPEC-5) | `electron/` | 동일 |

유지되어야 하는 불변식:
- 렌더러는 Node API를 갖지 않는다 (`sandbox: true`, `contextIsolation: true`).
- 모든 외부 프로세스 실행·외부 HTTP는 main에서만 일어난다.
- `pathGuard` 4-tier 신뢰 모델은 **완화되지 않는다**. 프로젝트를 발견했다는 사실만으로 새 경로가 신뢰되지 않으며, 프로젝트 루트 신뢰는 기존 다이얼로그 경유 경로(Tier 1–4)를 그대로 탄다. 에이전트/샌드박스가 요구하는 확장은 SPEC-3/5에서 명시적으로 다룬다.

### 문서 원칙과의 관계

`docs/DOCUMENT_MODE_PRINCIPLES.md`는 **문서모드 마크다운 편집**에만 범위가 걸려 있다. Epic은 그 밖의 파일(`.py`, `.csv`, `.bib`, `.json`)까지 바이트 무결성을 요구하므로 **원칙 문서가 아직 덮지 않는 영역**이 생긴다. SPEC-1은 이 공백을 기록하되 해당 문서를 재작성하지 않는다 — 원칙 문서 확장은 별도 작업이다.
